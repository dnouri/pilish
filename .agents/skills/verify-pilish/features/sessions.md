# Browse and resume sessions

The session and tree browsers support native folding, searching, copying, and scrolling. The session browser can resume a closed saved session and rebuild its history. When the selected file is already live in this Emacs, the browser displays its existing session instead. Reload restarts Pi for the open session and rebuilds the same history.

## Sub-features

- `session-browser` folds, searches, copies, and scrolls saved-session rows. Opening gathers metadata only. The first valid nonblank search gathers full text asynchronously; later queries reuse it, and refreshes and scope changes keep collecting it until buffer death or mode reset.
- `sessions-dir-env` selects a nonempty `PI_CODING_AGENT_SESSION_DIR` as flat local storage without a linked chat. Current project filters by saved cwd; All projects lists only that custom directory, not the default archive tree.
- `tree-browser` applies the same native actions to projected conversation nodes.
- `session-resume` selects a closed saved session in the real browser, invokes its switch command, and rebuilds the chat history.
- `session-live-row` marks a file with a live Pilish process in this Emacs with `●`. `RET` displays the existing owner and focuses its input, or its chat under hidden-input display, without sending `switch_session` to either process or changing the source session. Browser-only dismissal, source-guard bypass, same-owner activation, and hidden-input focus have focused unit coverage.
- `session-identity` lets custom observers follow initial session state, new-session, resume and a buffer rename observed on the next state refresh, without treating a symlinked spelling of the same saved file as a change.
- `session-alias-directory` keeps one buffer pair for a session started through a symlinked directory: opening its saved file, whose recorded cwd is the resolved path, and `M-x pilish` from the resolved directory reuse the pair under its first spelling.
- `session-state-ownership` keeps a newly selected session's identity and header state when an older startup or thinking-level state response arrives.
- `background-start` starts a new and a resumed session with `pilish-start-session`. Neither changes the window layout or sends a prompt; `pilish-show-session` later shows the resumed history.
- `session-reload` restarts Pi for the open session, keeps the unsent draft, and rebuilds the chat history. A Lisp caller's reload callback reports each reload exactly once, including a fresh Pi that exits.

## How to get to it (user POV)

- Use the margin, `TAB`, `S-TAB`, `/`, `M-w`, and ordinary scrolling in an open session or tree browser.
- Export `PI_CODING_AGENT_SESSION_DIR`, open `M-x pilish-session-browser` from a local project without starting Pi, and press `t` for All projects.
- Select a closed saved session and run `M-x pilish-session-browser-switch` to resume it.
- With two live sessions in one Emacs, press `C-c C-r` in one input window and `RET` on another row marked `●`.
- Register an observer with `pilish-session-identity-functions`, use `C-c C-n`, then open the original file with `pilish-open-session-file`.
- Run `M-x pilish` from a symlink to a project, then open the saved file with `pilish-open-session-file` and run `M-x pilish` from a file in the resolved directory.
- Use `C-c C-n` for a new session while a background state query is outstanding.
- Call `pilish-start-session` from Lisp, then show the session with `pilish-show-session`.
- Run `M-x pilish-reload` in a session, or call `pilish-reload` with a callback from Lisp.

## Gotchas

- Environment discovery applies only to local cwds; remote projects retain munged per-host storage. An empty variable keeps default storage. Pi's standalone `sessionDir` settings file is still unread without a linked chat. A linked chat's saved-file directory remains authoritative, including for the menu's own session listing; this change does not add settings-file discovery there.
- The env-browser journey uses isolated local JSONL files and never starts Pi; it proves browser discovery and scope filtering, not CLI storage configuration or remote access.
- The state-ownership journey controls delivery of real fake-Pi `get_state` responses to reproduce the interleaving. It calls the background thinking refresh directly; it does not cover the thinking selector's completion UI or claim that Pi replies out of order in every runtime.
- The large browser scenario uses 2,000 synthetic rows in each browser. It enters the modes directly with session search already enabled and does not prove first-search disk loading or resume those rows.
- Identity evidence uses the deterministic fake's actual RPC changes; it does not exercise real Pi or arbitrary buffer renames without a later state refresh. Its project directory uses its resolved spelling; the alias-directory journey covers a session started through a symlink.
- The alias journey covers a local symlink. Remote directories match only as written. An input buffer whose chat was killed is still found by its buffer name, so another spelling does not reuse it.
- PNG capture requires `x-export-frames`. Missing PNGs make the screenshot requirement blocked even when the assertions pass.
- The resume bench calls `pilish-session-browser-switch` directly. The live-focus journey covers `C-c C-r` and `RET`. These recipes do not cover the `/resume` or `C-c C-p w` opening aliases, cold-row `RET` dispatch, the `?` menu action, or Evil `RET`.
- The background journey passes no per-session arguments or environment, because the fake accepts no extra arguments. Unit tests prove both at the process boundary.
- The reload and resume scenario proves correctness only. Do not cite its timings as a performance result.
- The live-focus journey creates its second live session with a direct resume call during setup. The actions under test still use native `C-c C-r` and `RET`. The GUI test does not assert browser dismissal, window count, hidden-input display, aliases, or draft contents. The focused unit tests cover the guarded branches and dismissal rules. Live-marker layout has assertion logs only.
- The benchmark runner replaces its marked output directory on a later run. Always give it a new feature-owned directory.
